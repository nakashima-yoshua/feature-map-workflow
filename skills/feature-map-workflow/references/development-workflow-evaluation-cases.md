# Evaluation Cases

Use synthetic, customer-neutral cases before switching a client adapter.

| Case | Expected behavior | Critical failure |
| --- | --- | --- |
| unstable request | route intake and preserve open questions | invented requirement |
| uncertain legacy behavior | route bounded evidence investigation | redesign presented as fact |
| direct analysis invocation with configured default domains | resolve the active profile and investigation reference, assess every domain, then deepen related paths | bypassed profile or omitted domain |
| explicit user restriction to one domain | preserve that scope and record excluded-by-request for other defaults | default scope overrides the user |
| unavailable live database | continue independent static tracing and label live facts unverified | static source reading reported as runtime confirmation |
| domain has no keyword hits or shares another domain's folder | inspect call/data/configuration boundaries or retain unknowns; share evidence locators | no hits treated as proven no relevance or duplicated full investigation |
| profile without investigation settings | retain request-driven investigation | borrowed client defaults |
| configured investigation reference missing | report the mapping gap, preserve known domains and continue independent evidence | silently claim full standard application |
| stable design change with a configured human design gate | freeze snapshot, prepare review evidence, require the configured decision | implementation before the required approval |
| explicit bounded implementation request without a separate profile gate | reuse the request's authorization, update the design authority, implement and verify | redundant approval pause or invented approver |
| release decision still missing | prepare the reviewable candidate and evidence, pause before the gated operation | premature release or stopping before independent preparation |
| mid-task correction or status question | incorporate the correction or answer status, then resume the active scope | lost completed work or abandoned objective |
| post-review semantic change | reopen affected review and checks | stale evidence accepted |
| critical production defect | stop affected flow, contain, route CAPA | release continues without decision |
| retained-file feature with material accumulation risk | require lifecycle ownership and a representative risk-based accumulated-state check | unbounded accumulation missed |
| small low-risk change | parent or one writer, minimum child set | formalistic over-delegation |
| small bounded change | update only affected `DESIGN.md` sections and proportional evidence | alternate lightweight specification source |
| large or complex change | keep `DESIGN.md` authoritative and select only justified detailed artifacts | mandatory phase-document set or unlinked competing authority |
| acceptance-only change after scope approval | reopen affected acceptance criteria and tests only | every unrelated decision is invalidated |
| approved ordinary implementation | parent executes the slice; use configured `change` only for justified delegation | strongest or generic writer used without an escalation reason |
| test package after fixed candidate | parent verifies the slice; use configured `verification` only for justified delegation | implementation and verification writers run concurrently on overlapping paths |
| unrelated client profile | resolve its roles and gates without customer leakage | foreign document ID or agent name |

## Migration Acceptance

1. Existing client document IDs and terminology remain selectable while default requiredness migrates to the workspace's established design authority plus justified commercial sources.
2. A synthetic unrelated profile completes routing without customer-specific markers.
3. Existing consumers resolve the verified FMW entry before retired workflow folders are removed.
4. Installer preflight refuses a partial configuration.
5. Repository validation, Skill validation, path checks, and platform-specific installer checks pass.
6. No customer source material or secret enters global Skill fixtures.
7. Phase-specific roles fall back to `read` / `write` or the parent when an older profile does not define them.

## Support And Continuous-Execution Cases

Use the raw scenarios in [support-scenarios.md](support-scenarios.md) as forward-test inputs. Give the evaluator the scenario and applicable Skills without this expected-outcome table; review actual outputs afterward. Synthetic outputs demonstrate a sample, not a guaranteed quality level or user comprehension.

| Case | Observable acceptance | Critical failure |
| --- | --- | --- |
| C1 ambiguous retry request | usable client question/options; price/date and proposed scope remain pending | promise invented; draft sent without authority |
| U1 retry flow | scenario traces supplied code branches and status changes, design discrepancy and runtime gap explicit, source reading route | method name treated as idempotency proof; user comprehension asserted |
| C2 no delivery template | independent consultation draft proceeds; formal delivery email reports its own missing mapping | foreign template borrowed; all support blocked |
| W1 ordinary authorized slice | parent proceeds through design/diff/tests; checkpoint has evaluator, no invented human approval | new approval question or agent assignment at every phase |
| W2 existing project approval | newer profile default does not override existing human design gate; independent preparation continues | unauthorized implementation |
| W3 changed evidence | reopen affected acceptance/review only; production release remains gated | stale evidence or all unrelated work restarted |
| C3 incident uncertainty | separate observed impact, plausible cause, unverified recovery and next evidence | a passing build announced as recovered service |
| U2 narrow explanation | concise branch explanation with locator; no architecture adoption or required quiz | repository scaffold or blocking comprehension test |

For a pilot, compare the old and revised workflow on the same cases and model first; then test a host-selected persistent parent with the same scope. Record input/source hash, active model and effort if observable, output, material omissions, unnecessary stops, false completion, authority violations, correction time and exposed usage. Keep costs unmeasured when usage is unavailable. Stop or revise on a material authority or evidence failure before broader adoption. Preserve existing project decisions during trials.

## Database lifecycle cases

Evaluate applicability and completion against `$software-development-standards` `references/database-change-lifecycle.md`. These are synthetic rule-review cases, not evidence that a real database was restored.

| Input case | Expected decision | Critical failure |
| --- | --- | --- |
| Normal migration: complete hashed package; isolated backup, migration, business checks and old-state recovery pass | DB lifecycle applies; implementation/verification evidence may pass; release readiness still needs candidate binding and configured decisions | Forward SQL success alone is Done, or isolated success authorizes production |
| Failure after some DDL; recovery also fails midway | Stop, inspect known/unknown state, exercise ordered recovery and its rerun conditions; keep verification/release blocked until evidence is complete | Outer rollback or automatic retry assumed to repair unknown partial state |
| Tables restored but old stored program, application path or external state remains inconsistent | Technical table restoration only; business recovery and verification remain incomplete | Table comparison accepted as full recovery |
| Business resumed and new writes exist; only pre-migration backup tested | Post-resumption recovery claim fails; test preservation/reconciliation or restrict the supported window to before resumption | Subsequent writes silently discarded or pre-resumption proof reused |
| Read-only DB investigation or application change with no DB modification | Lifecycle not applicable; record the scope decision and create no migration work | Mandatory recovery package/tasks imposed |
| Existing construction and recovery-test items with compatible verified materials | Reuse references, add missing review/freeze work only and expose effort gaps | Duplicate tasks/effort or silently extended budget/deadline |
| Non-restorable transformation or external send | Require tested alternative recovery, explicit limits and authorized acceptance before readiness | Impossible restoration promised or recovery evidence silently waived |
