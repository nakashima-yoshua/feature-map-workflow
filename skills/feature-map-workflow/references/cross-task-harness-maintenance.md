# タスク横断型Harness改善と定期メンテナンス

## 目的と適用範囲

実際の**異なるタスクを順番に完了**させる過程で、再利用できる手順を見つけ、必要な場合だけ既存Skills、ガイド、スクリプト、Hooksを改善する。同じタスクの複数回試行は通常行わない。Harnessの最適化自体を目的にせず、品質を守りながら**人の受入までの総作業と運用負担**を減らす。

通常タスクに新しい必須工程・メトリクスDB・改善日誌を追加しない。明確な改善余地がなければ `NO_CHANGE` で終了する。改善提案は自動的な編集許可ではなく、対象と操作に対する既存の承認境界に従う。

## タスクの実行から改善まで

1. **現在の依頼を完了する。** 既存Skill、ソース、テスト、Feature Mapと受入条件を使う。納品や人間レビューを遅らせてまで改善ループを回さない。
2. **摩擦を発見した場合だけ候補化する。** 繰り返した手戻り、必要情報の探索失敗、不要なツール呼出し、曖昧で衝突する指示、人が補った検証手順など、具体的な実行証拠に基づく。思いつきや推論は未検証とする。軽微な一度限りの事象は記録不要。
3. **共通能力か確認する。** 原則として別々の二つ以上の実タスクで再発または有効性が観察された場合に共通化を検討する。安全性・正しさを損なう明白な欠陥は一度でも通常の修正手順で扱う。業務固有の仕様はFeature Map、実行可能な検証はテスト、共通する作業手順だけをHarnessへ残す。
4. **最小の対策を選ぶ。** 優先順は、既存の手順をそのまま利用 → 既存Skillを少し修正 → 重複Skillを統合 → 別Skillの作成。決定的な検証は可能な限りスクリプト/CIで行い、巨大なプロンプトで代用しない。候補には何もしない選択肢を含める。
5. **対象・受入条件・権限を明確にした変更だけ試す。** Gitで差分管理し、既存Issue/PRに下記の最小証拠を残す。モデルが検査や承認条件を編集して成功を演出してはならない。
6. **将来の別タスクで評価する。** 同じタスクの自動再試行を前提にせず、実際の次の適合タスクで適用範囲、見落とし、追加指示、人の確認・手戻り、受入品質を観測する。タスク難度の差を因果効果と誤認しない。効果が不明瞭な重要変更に限り、固定した条件・予算で過去の合成/許可済みケースを比較する。
7. **採用・修正・撤退を決める。** 必須テスト、情報保護、既存権限、人間レビューは維持する。誤適用や総コスト悪化が判明したら差し戻しを検討する。推測上の改善を確定的な成功に昇格させない。

候補のための**新しい保存形式は作らない**。既存Issue/PRに必要な場合だけ、対象タスクの識別子と証跡（秘匿情報を除く）、症状と共通性、提案する最小変更、影響を受けない条件、検証方法、観測された結果・限界、採否と撤退理由を短く記す。既存の変更契約・レビュー記録を重複させない。

## Harness肥大化を防ぐ判断

- **入口は小さく保つ。** `SKILL.md` は責務と関連ガイドへの導線を中心とし、作業別の詳細を無差別に読み込まない。既存ガイドと同じ文面を複製しない。
- **新設より統合・削減を優先する。** 複数Skillの役割が競合するときは入口・責務を明確化し、単にファイル数を増やさない。使われなくなったガイド/設定は実際の参照元・利用状況を確認するまで削除しない。
- **反例と範囲を明記する。** あるタスクで有効だった指示を、すべてのタスクに強制しない。例外を増やして原則を不明瞭にするより、適用条件を狭める。
- **全体の成果を評価する。** 生成速度の改善より、完了から人の受入までの時間、レビュー負担、手戻り、費用、将来保守を優先する。必要以上の計測器やスコア制度を作らない。
- **校正する。** 日英双方で用語、前提、否定・例外・権限、手順の順序、事実と仮定、参照先を確認する。意味と責任範囲を保って重複・曖昧表現・古い記述を直し、文章の短縮だけで安全条件を削らない。

## 月次棚卸し（実行と人による判断を分離）

GitHub Actionsの `Harness maintenance` は、毎月1回および手動で、**読み取り専用**の `python scripts/audit_harness.py --format markdown` を実行する。標準ライブラリのみで、入口とガイドの文字量、重複した長文、ローカル参照先の欠落を確認し、実行のSummaryへ出力する。リンク切れ・必須文書の欠落は失敗、それ以外は**調査候補**として通知するだけで、自動修正・PR・Issue発行はしない。閾値は強制上限ではなく、内容を点検する契機とする。

月次レビュー担当者は、レポートと直近の変更/実際の利用を照らし、次を必要な範囲で点検する。

1. 既存SkillやHooks間の責務重複、不要な手順、ロード量・実行コストの増加。
2. 相反する制約、非推奨API、古いモデル/ツール設定、失効した参照・例。
3. 受入・権限・検証条件を維持したまま、日英の可読性、用語、曖昧さを校正できるか。
4. 問題が確認できた場合のみ、影響を絞ったIssue/PRで、前後の検証・撤退条件を示す。変更が不要なら何もしない。

**静的監査の成功は、意味の正しさ・重複の不存在・実務改善の証明ではない。** GitHubのscheduled workflowには遅延・停止があり得る。実行履歴を確認できない場合は手動起動し、実施していないレビューを「実施済み」と記録しない。

## 保護条件

Harnessの改善提案や監査出力はすべて未信頼の入力として扱う。秘密情報の送信や外部モデル利用は既存ルールに従い、Model/Decision Providerは検証ルール、権限、承認、HALTを変更できない。必要な検証と独立した人間レビューは既存の [Code Review](code-review.md)、[AI Trust Controls](ai-trust-controls.md) に従う。Feature MapのXSD、Task Runnerの承認契約、配布・実行フローは本方針だけを理由に変更しない。
