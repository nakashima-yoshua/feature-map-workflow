# Evidence-based Maintenance Triage（保守改善の調査と小規模検証）

> **任意手順・初期は読み取り専用。** [OpenAI: Maintaining software with the GPT-6 family](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family) の事例を、既存の [YAGNI × 全体最適](yagni-whole-system-optimization.md)、[Legacy Analysis](legacy-analysis.md)、[Development Lifecycle](development-lifecycle.md)、[Code Review](code-review.md) の範囲に取り込む。記事中の効果やモデル間の優劣を、このリポジトリの実測結果とは扱わない。

## 適用条件と権限

- 保守負荷、CI遅延・不安定、不要なAI作業、未使用と疑われるコード・設定について**明示的に調査依頼がある場合だけ**実施する。通常の機能開発に追加の必須工程を作らない。
- 最初は対象リポジトリ・commit・ディレクトリを固定し、**読み取り専用**で候補を最大3件まで調べる。改善候補がなければ `NO_CHANGE` として終了する。全域スキャン、繰り返し調査、他システムへのアクセスは依頼範囲を広げない。
- 利用する根拠は許可された Source / Tests / Feature Map / Git・PR履歴 / CI履歴・ログ / 設定・デプロイ情報 / 実行時メトリクスに限定する。外部サービスや本番データへのアクセス、秘密・顧客情報のモデル送信は別途許可とデータ保護が必要。利用不可の資料を確認済みと書かない。
- **この手順は削除・設定変更・自動PR作成の許可ではない。** 調査から変更へ進む場合は対象・操作・検証条件について許可された範囲を確認し、既存の [AI trust controls](ai-trust-controls.md) と [Code Review](code-review.md) を適用する。

## 1. 読み取り専用トリアージ

1. 改善の目的、対象外、正確な基準revision、既存の痛点と観測可能な成果指標を決める。実測値がなければ「仮説」とし、削除行数・AI単価・指摘件数だけを成功指標にしない。
2. 現在の制約に近い候補から調査する。例: (a) `SKILL.md` / `AGENTS.md` / Hooks が誘発する不要なAI作業、(b) CI時間・不安定テスト、(c) 未使用疑いコード、期限切れ設定・Feature Flag。CIの一度の失敗だけで `flaky` と断定しない。
3. 各候補について次の最小限の証拠を示す。ソース・テスト・設定と履歴を横断し、証明できない点は未確認のまま残す。

| 必須項目 | 記録する内容 |
| --- | --- |
| 対象 | revision、`file:line` / symbol / 設定名、影響範囲とオーナー（判明時） |
| 現象と根拠 | 観測値・実行結果・CI/PR・コード参照。参照がないことと実行されないことは区別 |
| 利用・依存 | 呼び出し元、DB/設定/リフレクション/動的生成名、外部利用、権限・環境差 |
| 保護条件 | Kill switch、障害復旧経路、運用手順、重要なInvariant、トランザクション、ロールバック |
| 期待効果・費用 | 比較可能な基準値（あれば）、検証/レビューを含む総作業、推定と実測の区別 |
| 不確実性 | `CONFIRMED` / `INFERRED` / `UNVERIFIED` / `HUMAN_DECISION` と最小の次の確認 |

**削除の注意:** 静的参照が見つからない・通常時に実行されない・メトリクスがないだけでは未使用を証明できない。DB値・バッチ・API・設定・別サービス・非常時手順の間接依存を確認する。`CONFIRMED` は調査結果の根拠が確認できたことを表し、変更や削除の自動承認を意味しない。根拠が不十分なら削除PRを提案しない。

## 2. 候補の選別

- 最大3件を、**受入までの総作業時間・運用負荷への期待効果**、証拠の確実性、変更リスク、検証/人間レビュー工数、可逆性で相対評価する。金額・時間・CPU節約を推測で数値化しない。情報不足なら計測・調査を先に提案する。
- `NO_CHANGE`（根拠不足・費用対効果が低い・安全でない）、`SMALL_EXPERIMENT`（小さく検証可能）、`HUMAN_DECISION_REQUIRED`（業務意味・権限・高リスク）のいずれかを**判断結果として**示す。新しい永続状態やスキーマ値は増やさない。
- 採用候補は原則1件のみ。候補を網羅すること、調査件数や削除行数を増やすことは目的ではない。

## 3. 最小実験とA/B検証

- 選んだ候補1件の基準値、成功条件、保護条件、停止条件、後戻り方法を既存Issue/PR内で決める。変更する場合は独立した小さな差分にし、対象に近いテストから実行する。
- **AI指示が原因と考えられる場合のみA/B検証する。** 実際に誤誘導・不要作業が発生したCodexセッションと元の依頼があることを確認し、その1つの指示だけを変更候補にする。証跡がないなら「原因は未確認」とし、A/Bを実施済みとみなさない。
- A/Bは同一の基準commit・元の依頼・モデル/effort・ツール権限・テスト環境を使用し、分離した2実行（A=現行、B=対象の指示1箇所のみ調整）で比較する。セッションの独立性と環境差を記録する。**安全・権限・人間承認に関する指示は比較のためにも無効化しない。**
- 比較項目は、受入条件の達成・回帰/逸脱、不要なツール実行、トークン/API費用、実行時間、人間の追加確認・修正時間。取得できなかった指標は `NOT_MEASURED` とし、セッションを再現できなければ `NOT_RUN` とする。改善を実測なしで断定しない。
- モデル/effort比較は必要な場合だけ行う。利用可能なら低コスト構成（例: GPT-6.1 Sol Medium）を最初に試し、見落としや根拠不足が判明した場合のみ上位設定へ拡張する。モデル名による固定ルーティングは作らない。

## 4. 変更・レビュー・知識の扱い

- 調査結果は既存Issue/PRに簡潔に記す。構成や業務ルールの**再構築しにくい知識が新たに確定した場合だけ**Feature Map XMLを最小更新する。調査メモ・生ログ・ランタイム計測値の新しい正本を作らない。
- 変更するなら既存Phase 9のビルド・最小回帰テスト・CI・独立レビューを通し、承認範囲内で小さな**Draft PR**を作る。削除、Feature Flag変更、DB・公開インターフェース、本番構成変更は各対象の別途必要な権限・レビューを得る。マージ/デプロイは自動化しない。
- 改善前後を同じ測定方法で比較し、人のレビュー/待機や障害リスクへの負担転嫁も確認する。効果なし、品質低下、計測不能なら採用せず戻すか保留する。反復回数と予算はタスクごとに制限する。

## 最初の調査依頼例

```text
対象: 指定したリポジトリ/commit/ディレクトリ
目的: 品質を維持しながら保守・開発の総作業時間を削減する

まず読み取り専用で、AI指示による不要作業、CI遅延・不安定、
未使用疑いコード/設定のうち、根拠がある候補を最大3件調査する。
各候補に実際の source/CI/Git/設定の根拠、未確認の動的依存・
運用保護機能、期待効果・検証費用・人レビュー負荷を付ける。
最も価値があり安全に試せる1件の比較検証計画を示す。
根拠がなければ NO_CHANGE。コード・設定・本番環境は変更しない。
未実施の計測やテストは NOT_RUN / NOT_MEASURED と記載する。
```
