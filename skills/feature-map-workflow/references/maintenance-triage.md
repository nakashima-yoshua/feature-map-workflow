# 保守改善トリアージ：根拠を確認し、小さく試す

保守負荷や開発工程の効率について、調査を**明示的に依頼されたときだけ**使う。通常の機能開発に必須工程は増やさない。まずは読み取り専用で候補を絞り、変更の可否は別に判断する。

この手順は [OpenAIの保守改善事例](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family) を参考に、既存の [YAGNIと全体最適](yagni-whole-system-optimization.md) に沿って運用する。記事中の効果やモデルの優劣を、当リポジトリの実測結果として扱わない。

## 1. 改善対象と成功条件を絞る

1. **目的と範囲**：何の負荷を下げるか、守る品質・業務条件、対象と対象外、基準コミットを確認する。調査範囲は目的に必要な箇所だけ広げる。
2. **根拠**：許可されたソース・テスト・Feature Map・Git/PR・CI・設定・実行記録から確認する。まず最も可能性の高い対象を1件調べ、必要なら候補を最大3件まで増やす。
3. **測定方法**：変更の受入までにかかる時間、手戻り、レビュー負荷、運用負荷などから、今回の制約に合った指標を選ぶ。基準値がなければ「未測定」と記し、計測方法を提案する。

調査の例は、AIへの指示による不要な作業、CIの遅延や断続的な失敗、使われていない可能性があるコードや設定。1回のCI失敗だけでは不安定テストと断定しない。顧客情報・秘密情報の外部送信や、本番環境へのアクセスには別途許可と保護措置が必要である。

## 2. 「未使用」と「未観測」を区別する

候補ごとに**判断に必要な根拠だけ**残す。調査を複雑にするための報告書や網羅表は作らない。

- **対象と観測**：基準コミット、関係するファイル・シンボル、症状、参照できるログ・テスト・CI結果。
- **影響と依存**：呼び出し元、DB値・設定・リフレクション・バッチ・外部連携、権限や環境差。[Legacy Analysis](legacy-analysis.md) を必要な範囲で使う。
- **保護条件**：障害復旧経路、緊急停止用設定、業務上の不変条件、データ・トランザクションへの影響。
- **効果と負担**：期待する改善、必要な実装・検証・人間レビュー、残るリスクと復旧方法。

確かめた事実は `CONFIRMED`、根拠のある推測は `INFERRED`、調べられていない点は `UNVERIFIED`、人の業務判断が必要な点は `HUMAN_DECISION` と区別する。**静的な参照がないことや、普段の実行記録に出てこないことは、削除可能である証明にならない。** `CONFIRMED` も削除の承認ではない。

## 3. 変更しない選択を含めて優先する

確認できた候補を、受入までの総作業・運用負荷への効果、証拠の確実性、変更リスク、可逆性で比較する。推測だけで削減金額や効果時間を確定値にしない。

- `NO_CHANGE`：根拠が弱い、改善の価値が小さい、またはリスクに見合わない。理由を残して終了する。
- `SMALL_EXPERIMENT`：小さく安全に比較できる。**最も有望な1件だけ**を次へ進める。
- `HUMAN_DECISION_REQUIRED`：業務の意味、権限、削除や本番変更などで人の判断が必要。該当する変更を進めずに確認する。

これは既存の判断区分であり、XMLの状態や新しい承認制度は追加しない。

## 4. 必要な場合だけ実験し、総効果で判断する

実験する場合は基準値・合格条件・上限工数・停止条件・戻し方を既存Issue/PRに記す。承認された対象だけを変更し、近いテストから確認する。改善前後は同じ条件で測り、AIの速度だけでなく、人の待機時間・確認作業や品質への負担転嫁も確認する。

**AIへの指示が原因候補のときだけA/B比較する。** 再現に使える依頼と基準コミットを揃え、独立した実行環境で「現行指示」と「指示1箇所だけ変更」を比べる。モデル・推論設定・権限・テスト条件は可能な範囲で固定し、違いを記録する。安全・権限・承認ルールは変えない。

評価するのは要求の達成、回帰、不要なツール使用、時間、API費用、人の追加作業。1回の結果を一般化せず、再現性と比較条件の限界を示す。比較できなければ `NOT_RUN`、取得できない指標は `NOT_MEASURED` とする。

モデル選択を見直す場合も、特定モデル名や単価を固定ルールにせず、**必要な品質を満たす総費用**で判断する。効果を確認できなければ採用せず、保留または元に戻す。

## 5. 結果は既存のIssue・PR・CIへ戻す

調査の根拠、判断、未確認事項、実測結果を既存Issue/PRに短く残す。業務上の再利用価値がある知識が新たに確定した場合のみ、Feature Mapを最小更新する。調査記録用の新しい正本は作らない。

コードや設定の変更に進むときは、対象・操作への許可を確認し、既存の [Code Review](code-review.md) と [AI trust controls](ai-trust-controls.md) に従う。テスト・CI・独立レビュー・人間の承認を省略しない。**調査の依頼だけで削除PR、設定変更、マージ、デプロイを実行しない。**

### 最初の調査依頼例

> 指定リポジトリの保守負荷を減らしたい。対象コミットを固定して読み取り専用で調査し、AIへの指示、CI、不要の可能性があるコード・設定から、根拠のある改善候補を最大3件示してほしい。品質・人の作業時間・費用を比較し、最初に試す1件、または変更不要の理由を提案してほしい。実測していない効果は明示すること。
