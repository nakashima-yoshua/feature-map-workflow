# YAGNI × 全体最適：判断設計と段階的導入計画

> 状態: **Proposed / 設計・計画のみ（未実装）**  
> 対象: Feature Map Workflow と任意の Autonomous Task Runner  
> 実行計画: [Issue #8 — Autonomous Task Runner](https://github.com/nakashima-yoshua/feature-map-workflow/issues/8)

## 1. 目的と原則

全体最適とは、個々の工程やAIの性能を最大化することではなく、**要求を満たす変更を、安全かつ継続可能に人間が受け入れられる状態まで届ける能力**を高めることである。

YAGNI（You Aren't Gonna Need It）は、その目的に寄与すると確認できない機能・工程・文書・基盤を追加しないための制約とする。

- **何を実現するか**を先に定義し、何を高速化するかから始めない。
- 要素単体の性能ではなく、**入力→判断→実装→検証→人間レビュー→受入**の流れと相互依存を見る。
- 現時点で全体の成果を制限する要因に集中し、制約でない部分の局所的な非効率を許容する。
- 副作用、負担の転嫁、待機、手戻り、品質と将来の運用費を評価する。
- 現在・将来の時間軸を区別し、保守性・可逆性・対応余力を守る。
- 最適構造を固定せず、制約や目的が変われば再評価する。
- **改善しない／実装しない**ことを正当な結論として扱う。

目的自体、最適化の対象範囲、受益者と負担者も検証対象である。短期の開発速度を改善しても、顧客の品質やレビュー担当者の待機負担を悪化させるなら全体最適とは限らない。必要になれば運用から構造、さらに目的まで問い直す。

**YAGNIは安全性を削る理由にはならない。** 受入条件、Invariant、権限、必要な人間承認、テスト・復旧手段は削減不可の保護条件である。

## 2. 判断ループ（7原則を4段階で運用）

| 段階 | 核心となる問い | 使用する根拠・手法 | 結果 |
| --- | --- | --- | --- |
| **Purpose** | 誰の何を改善し、何を守るか。目的自体は適切か。 | 業務成果、受入条件、重要なInvariant、関係者・時間軸 | 目的・境界・保護条件 |
| **Constraint** | 今、何が全体成果を妨げているか。 | 工程・待機・手戻り・依存の観測。TOC、VSM、システム思考 | 制約仮説と証拠／未確認事項 |
| **Intervention** | 変更不要を含め、何が最小・可逆の対策か。 | 5 Whys、依存分析、効果・費用・リスク・副作用の比較 | 最小実験／変更なし／HALT |
| **Feedback** | 全体成果は改善したか。次の制約は何か。 | 受入後の実測、PDCA、再発・負担移転・将来費用の確認 | 採用・差し戻し・撤退・再評価 |

各手法は**症状に応じて選ぶ**。すべてのタスクへVSM図、因果ループ図、多基準スコア、振り返り会を義務付けない。

判断の原則:

1. **観測可能な事実と仮説を区別する。** 制約が不明なら大規模改修ではなく、まず最小の計測・調査を選ぶ。
2. **制約でない部分を最適化しない。** 例: コード生成の短縮でレビュー待ちが増えるなら、全体の完了時間は改善しない場合がある。
3. **選択肢は少なく保つ。** `NO_CHANGE`（見送り）、`SMALL_EXPERIMENT`（小規模実験）、`HUMAN_DECISION_REQUIRED`（判断待ち）を基本とし、構造変更は観測された必要性と承認がある場合に限る。これは判断上の分類であり、新たな永続状態モデルではない。
4. **他工程への負担と将来費用を隠さない。** トークン単価、AI作業速度、コード量だけで採否を決めない。
5. **改善後も制約は動く。** 以前の最適化方針を機械的に継続せず、次の改善をしない判断も許す。

## 3. 既存アーキテクチャへの接続設計

```text
人間の目的・リスク受容・承認範囲
  └─ System Understanding Architecture / Change Contract
       ↓
依頼 + 現行の Feature Map / source / tests / Git・CI証跡
       ↓
Purpose → Constraint（根拠/未確認）→ YAGNI判断
       ├─ NO_CHANGE ── 理由と必要な観測だけを返し、変更しない
       ├─ HUMAN_DECISION_REQUIRED ── 判断が済むまで影響範囲をHALT
       └─ SMALL_EXPERIMENT
            ↓
       Codex + 既存Skill/Hooks + 必要な場合のみTask Runner
            ↓
       既存テスト・CI・差分範囲・Invariant・副作用を検証
            ↓
       Human Review Request（根拠・不確実性・残存リスク）
            ↓
       人間が対象revisionを承認・差し戻し・保留
            ↓
       全体成果の再測定 → 採用／撤退／次の制約を再評価
```

**既存資産を再利用し、新しい正本を作らない。**

| 関心事 | 正本・責務 |
| --- | --- |
| 目的、業務意味、受入・リスクの責任 | [System Understanding Architecture](https://github.com/nakashima-yoshua/system-understanding-architecture) の要件・設計・Change Contract・Human Review Request |
| 永続するFeature知識、探索入口、未解決事項 | [Feature Map XML](feature-map-contract.md)（コード等から再構築しにくい事項だけ） |
| 実装と期待動作の検証 | Source / tests / CI。事実と実行結果の正本 |
| 実行制限、繰り返し試行、途中状態 | [Autonomous Task Runner計画（Issue #8）](https://github.com/nakashima-yoshua/feature-map-workflow/issues/8)。導入する場合も一時的な実行状態をFeature Mapに保存しない |
| 承認された変更・履歴 | Git commit / PR / 人間レビュー。AIの自己評価は承認ではない |

既存の [Development Lifecycle](development-lifecycle.md) の入力、Hard/Semantic Gate、HALTを利用する。最適化専用の新しい工程列、XMLモード、DB、ジョブキュー、必須の改善シートは追加しない。[Test Strategy](test-strategy.md) と [Coverage Model](coverage-model.md) の最小・実行可能な保証を維持する。

### 最小の判断契約（新ファイルの強制なし）

既存のChange Contract、Issue、またはPRの適切な場所に**必要な項目だけ**記す。軽微で明白な修正には項目の再記述を要求しない。

| 項目 | 最小の問い |
| --- | --- |
| 目的・対象範囲 | 何を、誰のために実現するか。対象外は何か。 |
| 全体成果の指標 | 何を測れば改善と分かるか。測定不能なら何を仮説とするか。 |
| 現在の制約と根拠 | どこが制約か。観測済みか推論か、未確認か。 |
| 最小の変更案 | 変更しない案、局所対策、可逆的実験のどれか。 |
| 保護条件と副作用 | Invariant、品質、権限、他工程の待機、顧客負担、復旧可能性。 |
| 検証・採用・撤退条件 | 実験の観測範囲、比較対象、停止・撤退、人の判断が必要な点。 |

複雑な変更でこれらが欠落し、結果・権限・重大リスクを左右する場合のみ質問・HALTする。独立した「最適化文書」を毎回作らない。

### AIと自動処理の権限境界

- **人間:** 目的の妥当性、業務上の価値・許容するトレードオフ、重要なInvariant、リスク受容、承認、リリースを決める。
- **Codex/LLM:** 制約候補・因果仮説・最小案を説明し、許可範囲内で調査・実装・検証・証跡準備を行う。仮説を事実に昇格させない。
- **OpenAI Decisions API（移行計画中）:** `DecisionProvider` 経由で文脈充足、変更後に残す知識、人レビューの必要性**などの限定的な助言**に使う。制約の実在判定、ROI認定、権限、HALT解除、テスト合否、承認には使わない。既定は`off`、外部送信は明示許可。Jev置換の詳細はIssue #8。
- **決定的なツール/ルール:** テスト合否、XSD、Git revision、変更範囲、実行上限、権限、保護条件、承認の有無を確認する。
- **人間レビュー:** 変更の目的から実装へ降りて確認する。証跡は `CONFIRMED / INFERRED / UNVERIFIED / HUMAN_DECISION` を区別し、AIの自己承認を認めない。

必要な権限・承認が欠ける、重要な正本が矛盾する、Invariantや復旧可能性を保てない場合は、成果指標が改善していてもHALTする。

## 4. 測定設計：局所性能でなく流れを見る

**主指標の候補:** 依頼を着手可能と判断してから、必要な検証と人間の受入判断が終わるまでのリードタイム。対象と開始・終了の定義を変えずに比較する。

**必要時の補助指標:** 実装/検証/レビューの待機、手戻り件数、欠陥流出、受入済み変更1件当たりの総作業時間・API費用・人件費、レビュー差し戻し率。AIの出力速度や単価だけでは評価しない。

**必須の保護条件:** 受入条件、業務Invariant、安全・機密保持、権限、人の承認、復旧可能性。改善によって悪化した項目・未計測項目を明示する。平均値だけで一部の重大な失敗を隠さない。

- 新しい収集基盤は作らず、既存のIssue/PR/Git/CI/Runner記録から得られる数値で開始する。
- 比較対象がない場合は「改善を実証した」と言わず、計測可能な小規模実験を先に行う。
- 制約を改善した結果、レビューや別工程へ待機が移れば、全体成果で再判断する。
- コスト測定のために大きな監視基盤や新しいメトリクスDBを導入しない。

**例:** AIのコード生成だけが30分短縮されても、レビュー待ちが2時間増えれば、他条件が同じ限り全体のリードタイムは悪化する。まずレビューに必要な情報の不足・確認の手戻りを調べ、レビュー権限そのものを省略してはならない。

## 5. 段階的な導入計画（Issue #8と対応）

新しいPhaseや独立したプロジェクトを増やさず、Issue #8の既存計画へ横断適用する。

| 段階 | 最小の変更 | 完了・継続判断 |
| --- | --- | --- |
| **Phase 0：設計** | 本文を人がレビューし、全体目的・制約・YAGNI・保護条件・変更不要の判断を既存のChange Contractと人間承認契約へ対応付ける。 | 新しい正本／XML項目／承認基盤なしで「進める／見送る／HALT」の区別を説明できる。 |
| **Phase 1：単一タスク** | リスクの低い既存タスク1件で、基準値、制約仮説、最小修正、テスト・人レビューの結果を既存Issue/PRへ記録する。計測不能ならまず調査する。 | 実装しない選択肢も含め、目的・根拠・影響・検証結果を人が追跡できる。追加のRunner機能はこの判断のためだけには作らない。 |
| **Phase 2：限定的反復** | 自動評価可能で再試行が有効な仕事に限り、Issue #8の上限付きRunnerを適用する。各試行の性能とともに受入までの総時間、レビュー滞留、保護条件を比較。 | 局所改善が総成果を悪化させる場合や改善効果が不明な場合、反復を停止・見直せる。 |
| **Phase 3：効果測定** | 少数の代表タスクで前後比較。再試行・人の介入・欠陥・費用を記録し、制約が移ったか判断する。 | 効果が確認できなければ`off`/手動運用へ戻す。効果があり需要が増えた場合だけ次の拡張を検討する。 |
| **Phase 4：将来** | 複数タスク・キュー・Projection等は、実測で単一タスク運用が制約と確認された場合だけ検討する。 | 需要と投資対効果がなければ実装しない。 |

### 先に確認するシナリオ（設計の受入条件）

1. **制約がない／根拠不足:** 変更せず、必要な観測だけ提案できる。架空のROIを報告しない。
2. **明らかな軽微修正:** 重い分析資料・多基準スコアを作らず、既存テストで安全に済ませられる。
3. **AI高速化でレビュー滞留が増加:** 局所的な速度向上を全体最適と誤判定しない。
4. **性能向上だがInvariant違反:** 採用しない。テスト条件を書き換えて成功扱いしない。
5. **承認不足／リスク拡大:** OpenAI Decisions APIの助言にかかわらずHALTし、人に判断を返す。
6. **反復失敗／計測不能:** 無限再試行せず、予算内で見送り・停止・人レビューへ移行する。
7. **環境・需要の変化:** 前回の制約解消後に対象と目的を再評価し、同じ最適化を続けない。

## 6. YAGNIによる非目標と撤退条件

今回の計画・設計追加では、実行エンジン、Hook、新しいDecision APIアダプター、Feature Map XSD、UI、Queue、SQLite、BaseX、複数Agent、専用メトリクス基盤は変更・追加しない。

将来の導入では、次のいずれかなら拡張を見送る。

- 全体指標への寄与が説明できない、または既存手段で十分である。
- 自動化の維持・レビュー・トラブルシュート費用が削減効果を上回る。
- 測定不能な重要リスクを人が受容していない。
- 既存の責務分離や承認境界が弱まる。
- 実運用の新たな制約ではなく、将来への推測だけが導入理由である。

**最終原則:** 目的に対して最も影響が大きい現在の制約を、小さく、可逆に、証拠に基づいて改善する。改善しない判断も成果として尊重し、全体の受入能力が向上したかを測定してから次へ進む。
