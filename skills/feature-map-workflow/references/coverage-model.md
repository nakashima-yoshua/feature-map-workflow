# Coverage Model

## Purpose

Measure whether meaningful behavior is protected, not merely how many source lines executed.

Do not collapse all quality signals into one overall coverage percentage. Keep separate denominators so missing protection remains visible.

## Coverage dimensions

Use these primary denominators:

1. **Requirement coverage** — accepted requirements / done conditions.
2. **Scenario coverage** — materially distinct business scenarios.
3. **Rule coverage** — business rules and decision outcomes.
4. **State / boundary coverage** — state transitions, equivalence classes, boundary values, error/retry/duplicate conditions.
5. **Effect coverage** — required observable side effects such as DB updates, events, files, messages, or external requests.
6. **Dynamic-route coverage** — runtime-selectable paths discovered from DB/configuration/reflection/process dispatch/events/jobs.
7. **Code coverage** — branch/method/line coverage as a residual leak detector, not the primary quality score.

## Denominator rule

Add an item to a denominator when changing that condition can produce a meaningfully different:

- business result;
- decision;
- state transition;
- side effect;
- failure mode;
- authorization outcome;
- external interaction;
- recovery/retry behavior.

Do not count every syntactic branch if several branches are equivalent from the protected behavior's perspective.

Use equivalence classes and boundaries instead of all possible input values.

Example:

```text
quantity domain
  negative
  zero
  valid minimum
  normal
  maximum
  above maximum
```

These may form six useful denominator items even though the underlying numeric type has billions of possible values.

## Traceability

Maintain traceability conceptually as:

```text
Requirement
  -> Scenario
  -> Rule / State / Effect / Dynamic Route
  -> Test
  -> Evidence
```

Feature Map IDs can serve as stable anchors, but do not duplicate full test catalogs in XML.

Generated reports may calculate, for example:

```text
Requirements       42 / 42
Scenarios          18 / 18
Rules              73 / 76
State / Boundary   21 / 22
Effects            31 / 31
Dynamic Routes     12 / 17
Code Branch        68%
```

Do not persist these percentages merely because they changed. Generate them from current evidence where possible.

## Possible, observed, and unknown

For legacy or dynamic systems, distinguish:

- **Possible:** a path can exist based on source, DB, configuration, deployment data, or static analysis.
- **Observed:** the path actually executed in a representative run or trace.
- **Observed-only:** execution occurred but static/configuration analysis has not yet explained why.
- **Unknown / unresolved:** the dependency or condition is not yet explained or verified.

Never treat an unobserved possible route as dead code merely because a test did not execute it.

Keep unresolved counts visible beside coverage. For example:

```text
Dynamic routes: 12 / 17 observed
Unresolved dependencies: 3
Observed-only routes: 1
Unverified external interfaces: 2
```

A high percentage must not hide an unknown area.

## Coverage and test layers

Do not map one coverage dimension to one test layer mechanically.

Typical placement:

- scenarios -> mostly E2E;
- rules -> mostly integration/service, sometimes unit;
- state/boundary -> integration/service/DB, sometimes unit;
- effects -> integration/E2E/DB;
- dynamic routes -> integration/runtime observation;
- code coverage -> generated by tooling across test suites.

Coverage is about the guarantee. Test level is about the cheapest reliable place to prove it.

## Source discovery in legacy systems

When specifications are incomplete, build denominator candidates from the union of:

- documented requirements;
- source conditions and switches;
- PL/SQL branches;
- DB constraints and triggers;
- code/master tables and sentinel values;
- configuration-driven paths;
- runtime traces;
- production-like examples and logs;
- operator procedures.

Classify each candidate as confirmed, duplicate, irrelevant, obsolete candidate, environment-specific, or unresolved before treating it as a committed denominator item.

## Completion guidance

A phase is not complete merely because code coverage exceeds a threshold.

Prefer completion criteria such as:

- all required scenarios have evidence;
- all high-impact rules/states/effects have a verification path;
- uncovered denominator items are explicitly accepted or blocked;
- unknown/unresolved areas are visible;
- code coverage contains no surprising unexecuted implementation in changed/high-risk areas.

Thresholds remain project policy and should be evaluated on representative project history rather than treated as universal quality facts.
