# 顧客提出資料の作成

## ソース・DB資材を含む提出版の固定

ソース差分の提出では、既存の案件記録に差分起点SHA、対象SHA、採用・除外条件、同梱資料の元ファイルを記録します。ブランチ名は版の識別に使いません。自動登録SQL、手動登録用SQL集、XML等の納品形式は、既存の合意と顧客の操作方法から選びます。形式変更時は説明書と必要な操作確認も見直します。

1. 指定された生成スクリプトは実行前に読み、対象版、除外条件、空差分、タグ作成・push等の副作用を確認します。ソースは固定SHAから取得し、ファイル一覧にも同じ条件を適用します。削除・改名は適用上必要な一覧に残します。
2. DB資材・説明書・試験結果も採用元とhashを固定します。顧客向け派生版は原本と区別し、古い候補や開発用復旧オブジェクトをフォルダーごと混入させません。
3. 最終ZIPを開き直し、採用一覧、除外対象の不在、各ファイルhashを照合します。説明書の「今回の版」、件数、ファイル名、添付参照も実物と照合します。過去の試験対象SHAは書き換えず、現在版への適用範囲を説明します。
4. 修正後は新しい候補として再生成し、固定タグや提出済み資材を上書きしません。生成・検査・アップロード・受領は別の実績として記録します。

納品メールは採用要件と添付実物から作り、同時納品の小さな改善も漏らさず要約します。アップロード済み・検証完了等の記載には、その実績の証拠が必要です。

顧客へ提出する試験設計・結果報告・説明資料を、既存の設計・実行証拠から作る場合に使います。内部技術帳票をそのまま提出せず、相手が判断・操作するために必要な内容を選びます。資料作成の依頼は、送信・公開・受入承認の権限を追加しません。

## 作業の振り返りから反映した点

- 技術用帳票には環境・接続・内部識別子が含まれる。作成前に顧客向けの項目を決め、別名の派生版として作る。
- セルの修正だけでは管理用語や参照が残る。納品対象ファイル全体と添付範囲を検査する。
- テンプレートの数式・集計・表示は、文面の正しさと別に確認する。
- 設計資料の完成、機能試験の実施、業務受入、顧客提出は別の事実。裏付けのある状態だけを記載する。

## 1. 提出範囲を決める

会話・契約・既存資料から、読者、用途（設計確認／実施記録／結果報告等）、必要な成果物、書式、対象機能、版を確定します。判断を変える不足だけを質問し、既知の条件を再質問しません。顧客原本・内部帳票・既存の実結果を保全します。

| 顧客向けに載せる内容 | 内部索引に残す内容 |
| --- | --- |
| 業務目的、対象と対象外、操作、入力条件、期待結果 | ソース版、内部要求・検証ID、開発管理情報との対応 |
| 外向けの試験番号・条件番号、実施状態、実観測、未解決事項 | run ID、原本の所在・hash、環境・接続・準備・復旧記録 |
| 提出範囲内の説明・顧客用証跡番号 | 生成元・テンプレート版、変換手順、検査結果、配布履歴 |

既定で開発PC・ローカルパス・接続先・認証情報・内部リポジトリ・Gitea/GitHub等の管理ツール名・Issue/PR・内部管理番号を除きます。顧客の業務に必要な権限や操作条件は残し、既存機能の利用と今回の変更を区別します。顧客が明示的に求めた技術情報は、開示範囲を確認して必要なものだけを記載します。

文書の版・作成日と、製品の検証対象版を混同しません。外向け番号と内部IDの対応表は非公開で保持し、項目の並べ替えで番号を再利用しません。網羅性は除去後も内部で照合し、顧客版に載せない検証を免除・合格扱いにしません。

## 2. 顧客版を別生成する

資料の目的に必要な種類だけを作ります。Excel、Word、PDFの一式を無条件に増やしません。提供されたテンプレートがある場合は出典・hashと対応レイアウトを確認し、原本は上書きしません。

試験設計は、仕様・リスクに基づく必要十分なケースと条件、操作、期待結果を示します。試験結果は、条件別の実観測・証跡があるものだけを転記します。過去版の実績、ビルド成功、帳票検査成功、全体PASSを、今回の未実施条件の合格へ転用しません。未実施・不合格・保留は消さず、資料上でも区別します。

Excelは [Functional Test Excel](functional-test-excel.md) を使います。同ガイドのCLIは技術用の出力なので、顧客版への変換が必要です。結果取込は内部IDを持つ技術用帳票で行ってから顧客版を生成します。内部IDを除去した顧客版へ技術用`results`コマンドを直接適用しません。手入力済みの判定を保護し、新版は別ファイルへ出力します。

画像や証跡の添付が必要なら、原本を保存したまま、必要範囲を選択・マスクした派生コピーを作ります。元hash・派生hash・編集内容を内部で対応づけ、マスク後の画像を目視確認します。原本スクリーンショットや内部索引を丸ごと同梱しません。

## 3. 最終ファイルを検査する

検査は実際の提出候補に対して行い、内部にコマンド・結果・対象hash・未確認範囲を残します。内容の修正や再保存後はhashが変わるため、影響する検査をやり直します。

| 検査 | 確認内容 |
| --- | --- |
| 内容と対応 | 原資料との一致、要求・ケース・条件の対応、必要な正常・異常・境界・権限、期待結果、対象外、実施状態。削除後に番号・参照・件数がずれていないこと |
| 内部情報 | 本文・全セルだけでなく、シート名、非表示のシート/行/列、コメント、ヘッダー/フッター、図形、名前定義、プロパティ、ハイパーリンク、外部参照、接続、添付・埋込まで確認 |
| 数式と集計 | 必要なテンプレート数式・書式・入力規則を維持し、Excel等の対応アプリで再計算して数式エラー・集計対象・未実施の扱いを確認。数式を固定値に置換しない |
| 表示と印刷 | 対応アプリまたはPDF等へ描画し、見切れ、改ページ、印刷範囲、文字サイズ、図、凡例を確認。対象シート/ページを記録し、代表確認だけなら全ページ確認済みとしない |
| 提出パッケージ | ファイル名・フォルダ名・同梱一覧、リンク先、顧客用証跡番号の到達性、ZIP/PDF等へ変換した最終成果物も検査。内部カタログや生成スクリプトを混入させない |

Office Open XML（xlsx/docx等）はZIPパッケージとして全XML・relationships・プロパティ等を走査します。標準スキーマのnamespace URIは管理情報とは区別し、表示文字列・リンク先・属性値の漏れを確認します。画像・OLE等のバイナリは文字列検索だけでは検査済みになりません。必要な内容を確認できない埋込は提出版から外すか、確認可能な別形式にします。Wordは変更履歴・コメント・文書プロパティ、PDFはテキスト・注釈・添付・メタデータも対象にします。

検査語は案件の禁止語・内部ID・既知の接続/パス情報から選びます。禁止語を消しただけで合格とせず、業務上必要な説明と文意の保持も確認します。検査ツール、数式再計算、描画のいずれかが利用不能なら、代替方法と未確認範囲を明示し、完了した検査を捏造しません。必要な確認が未完了なら提出候補は保留し、実施済みの準備までを渡します。

## 4. 固定して内部証跡につなぐ

[Evidence Storage](evidence-storage.md) に従い、提出候補と検査記録を`artifact-check`として選択保存します。顧客用番号→内部カタログ→実行条件→原本の対応を保持します。帳票の検査は製品の機能合格を意味しません。

内部記録は次を含めます。既存のカタログ・manifest・案件文書に追記できれば、別の台帳は作りません。

- 対象・用途、原資料とテンプレートの固定参照、生成元の版。
- 顧客版のファイル名・SHA-256・外向け番号と内部IDの対応。
- 内容・内部情報・数式・表示・同梱範囲の検査結果と対象hash、未確認事項。
- 現在の段階（作成済／検査保留／提出候補固定／提出済／受入済）と、その事実を裏付ける記録。

提出候補を固定する条件は、用途に必要な検査の完了、内部情報の除去、判定の裏付け、未実施・不合格・未確認の明示です。設計確認用資料は機能試験未実施でも作成できます。未完了項目を含む報告の提出可否は契約・依頼内容に従い、資料の完成を製品受入と扱いません。

## 5. エビデンスが揃った提出資材を整理する

資料作成・検査の後、送信の前に行う独立した整理工程です。対象は資料・添付証跡・提供ファイル等、今回の提出範囲に含まれる資材だけとします。既存フォルダを丸ごと転送せず、資材単位で採用を判断します。

**採用条件:** 最終候補のファイルhashが固定され、用途に必要な検査記録と、その記載・主張を支えるエビデンスへ辿れること。証跡ファイルの実在・hash・対象版・対象範囲を確認し、同じ名前の別版や過去版を根拠にしません。検査記録の存在だけでは、その対象hashの一致を省略できません。

| 資材の用途 | 採用に必要なエビデンス |
| --- | --- |
| 試験設計・説明資料 | 根拠となる仕様/確認記録と、当該最終ファイルの内容・内部情報・必要な数式/表示等の検査記録。未実施の計画は計画用途に限定し、機能合格の資材に分類しない |
| 実施結果・証跡 | 対象条件・対象版に一致する実観測、判定、原本。成功だけを選別せず、不合格・保留の実観測も正しい状態で扱う。未実施条件は未実施と表示し、実施済みの証拠にしない |
| ソース・実行物・設定等の提供ファイル | 提供範囲・固定版・実ファイルhashと、その用途に必要なビルド/検査/動作確認記録。ビルド成功だけで未実行の動作を保証しない |
| マスク・抜粋した添付 | 元原本との対応、派生hash、編集内容と編集後の内容・表示・内部情報の確認記録 |

根拠なし・ファイル欠落・hash/対象版不一致・必要な検査未実施の資材は、提出用フォルダへ入れません。内部の選別記録に資材名、除外/保留理由、不足証跡、次の確認を残します。必須資材が欠ける場合は全体を「整理保留」とし、揃った一部だけで提出準備完了としません。任意資材の除外で試験失敗や未解決事項を隠さないよう、必要な説明を本資料へ残します。

1. 内部の選別一覧で、候補ごとの用途・版・必須/任意・hash・検査記録・根拠証跡・採用/保留を確定する。既存カタログ/案件文書を再利用できれば新台帳は作らない。
2. 新規の版別パッケージ領域の`customer/`へ、採用した顧客向けファイルだけをコピーする。原本は移動せず、旧提出版を上書きしない。内部一覧・カタログ・ログ・生成スクリプト・未加工の原本はこのフォルダの外に保持する。
3. 顧客用の資材一覧（ファイル名・用途・顧客向け版/証跡番号）と実ファイルを照合する。この一覧自体も顧客向け資料として検査し、内部のhash対応表や管理IDを転記しない。
4. 一覧とフォルダの双方向照合で、不足・余分なファイル・旧版・非表示の作業ファイル・重複を除外する。全採用ファイルと顧客用一覧のhashを内部manifestに固定し、コピー元とコピー先の一致、顧客用リンク/証跡番号の到達性を確認する。
5. ZIP等が必要な場合は、検査済みの`customer/`内の確定一覧だけから生成する。アーカイブの全entryと解凍後のhashを内部manifestと照合し、階層・名称・メタデータも確認する。追加・差し替え・再保存があれば新しい候補として影響する検査と照合をやり直す。

出力は「証跡確認済みの提出候補一式」「顧客用資材一覧」と、外へ出さない「選別・除外記録、hash manifest、証跡対応」です。内部manifestと確定した一式/ZIPのhashも [Evidence Storage](evidence-storage.md) の内部記録へ結びます。資材整理の完了は送信・製品合格・顧客受入を意味しません。

## 6. 提出と改訂を区別する

作成結果は提出ファイル、主な検査結果、残る未確認事項として提示します。送信・公開は既存の明示的な権限と宛先・送付範囲に従います。実際に送った後だけ、固定ファイルのhash、宛先、日時、送信記録を内部に登録します。生成・PR・タグの存在だけで提出済みや受入済みにしません。

改訂時は前提出版を保持し、新しい版とhashを採番します。旧版の実施結果・人手判定を無条件に引き継がず、対象条件・検証対象版との一致を確認します。ローカル成果物を戻す場合も原本と送信履歴は消しません。
