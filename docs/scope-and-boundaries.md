# FMWの責務とリポジトリ境界（Scope and Repository Boundaries）

> **位置付け:** feature-map-workflow（FMW）が引き受ける責務と、関連ツールへの分離判断を定義する。
> **この変更の範囲:** 方針の文書化のみ。既存実装・利用経路・権限・XML形式は変更しない。

## 目的と成功条件

**FMWは、ソフトウェアの業務機能を継続的に理解・変更・検証できるように、機能単位の永続的な知識と根拠への参照を保守する。**

English summary: FMW is a source-first, per-feature durable knowledge and traceability layer—not a general-purpose workflow scheduler, autonomous development platform, test executor, or release authority.

新しく参加した開発者やAIが、過去の会話や実行ログを再生しなくても、次の問いに必要な情報へ到達できる状態を目指す。

1. **目的:** 機能が何のために存在するか。
2. **振る舞い:** 重要なシナリオ・業務ルール・例外は何か。
3. **構造:** 関連するソース、DB、API、テストはどこか。
4. **制約:** 変更時に保持すべき不変条件・互換性は何か。
5. **根拠:** どの仕様・ソース・実測・証跡に基づく理解か。
6. **未解決事項:** 何が未確認で、次に何を確認すべきか。

成功は文書の量ではなく、**必要な機能を素早く特定し、根拠をたどり、安全な変更と次の作業への引き継ぎができること**で判断する。不要な情報をXMLへ複写しない。

## FMWが所有するもの

- 業務上まとまりのある**1機能につき1つのFeature Map XML**と、その形式・検証・最小更新規則（互換性を含む）。
- 機能の目的、ユースケース、確認済みルール、不変条件、重要な設計判断、制約、影響先、未解決事項。
- コード・テスト・DB・要求・意思決定・証跡への**識別子と版付きの参照**。詳細な原物や履歴は複製しない。
- 根拠を伴う小さなMermaid/UML等の図と、XMLからの人向け表示・メタデータ索引。
- 機能知識を収集・照会・更新するための軽量なツールと、その利用ガイド。
- FMWに接続する任意のアダプター（Hooks、XML問い合わせ等）。**Coreでの利用を妨げる必須依存にしない。**

FMWのガイドは既存機能分析、変更時の確認、設計・テスト・監査への参照方法を案内できる。ただし、**工程の全タスク実行や組織の承認プロセスをFMWが所有することにはならない**。

## FMWが所有しないもの（正本の境界）

| 情報・実行責任 | 正本・責任主体 | FMWが行うこと |
| --- | --- | --- |
| 合意済み要求、業務の期待結果、変更許可、リスク受容 | プロジェクトの要求・Change Contract・権限を持つ人 | 対応するID・参照・重要な制約を保持 |
| 実装と実際の挙動 | 対象プロジェクトのソース・設定・DB・テスト | 実在する入口・影響関係を案内 |
| テスト計画の全件、実行、再試行、ログ・画面証跡の採取 | テスト基盤と元の結果・証跡ストア | 代表的な検証ケースと結果への参照 |
| AIタスクのキュー、スケジューリング、隔離実行、再開、ロック | 独立した実行・調整基盤 | 機能に関する入力情報を提供し、確定した知識差分のみ受け取る |
| 横断的な品質基準、ゲート判定、リリース可否の決定 | 品質基盤と人の承認 | XML/XSDの形式検証と根拠の参照を提供 |
| PR、CI、デプロイ、納品、承認、Git履歴 | Git・CI/CD・リリース記録・権限者 | 対象の正確なリビジョン等を参照 |
| 全社的な監査業務・証跡保管期限・アクセス権 | 監査担当者・証跡正本の管理者 | 参照可能な追跡経路を示す |
| 汎用のUML解析・図の分割統合・形式変換エンジン | 必要に応じた独立ツール | 機能理解に必要な図を参照・表示 |

重要: **FMWのXMLはジョブキュー、進捗台帳、再試行履歴、ログ保管庫ではない。** FMWが提供するXSD検証は、総合品質ゲートや業務上の承認の代わりにならない。HTMLは人向け出力であり、AI・外部ツールはXMLと構造化された正本を読む。

## 探索・開発・改善との関係

探索（Explore）は価値・要求・方針を見極め、開発（Build）は合意済み要求を実装・検証し、改善（Improve）は運用結果から次の処置を決定する。これらの**プロセス管理と状態遷移は外部のワークフロー実行基盤の責務**とする。

FMWは各プロセスに共通する機能知識を提供する。

- **Explore:** 現状の振る舞いと未知事項を示す。新しい仮説やアイデアを承認済み仕様として記録しない。
- **Build:** 対象機能、変更すべき保証、不変条件、関連コード・テストへの参照を提供する。承認された変更と検証で確定した知識だけを反映する。
- **Improve:** 実測値や不具合の正本を参照し、確定したルール・判断・重要な未解決事項を更新する。改善施策の実行キューを持たない。

既存の `catchup` / `change` は**Feature Mapの作成・更新目的**であり、Explore / Build / Improve という**案件の工程状態**と同一視しない。XMLの `state` も機能知識の検証状態であり、外部ジョブの状態ではない。この整理だけを目的として新しいXML属性や別の台帳を増やさない。

**既存の別リポジトリを優先して評価し、実体のない分割先を先に増やさない。** 新規リポジトリは独立した所有者・入出力契約・テスト・リリース理由が明確になった場合に限って提案する。

## 新機能の配置判断

次の順で判定する。

1. **知識の正本か。** 機能理解に必要な耐久的ルール・参照・図の維持ならFMW内。
2. **FMWなしでも独立して使えるか。** 汎用の実行、品質判定、スケジューリング、図変換なら外部化を優先。
3. **独立した権限・依存・障害対応・リリースを要するか。** 要するなら別リポジトリの理由が強い。
4. **FMW固有の薄い接続か。** XML入出力や参照だけの小さなアダプターなら任意機能としてFMWに残せる。
5. **既存利用者を壊さないか。** 分離先が未完成なら即削除せず、境界の明記と移行条件の定義を先に行う。

例:

- 機能のルールや制約をXMLに追記する → **FMW**。
- その機能のシーケンス図を根拠付きで保存・表示する → **FMW**。
- 大規模システムの任意の図を解析・分割・統合して生成する → **独立ツール候補**。
- テストのケースIDと証跡URIを関連付ける → **FMWの参照**。
- 試行のバッチ実行、ログ採取、リセット、再試行 → **テスト基盤**。
- XSDを現在のXMLに適用して検証する → **FMWの形式検証**。
- CI・テスト・リスクを総合評価しマージ可否を決める → **外部Quality Gateと人の承認**。

## 分離時の最小契約と移行条件

- **入力:** 権限のある要求・変更対象、FMW XMLから必要なノード、実在するソース・テスト・制約への参照。FMW生成HTMLを機械入力にしない。
- **外部の出力:** 状態・ログ・チェックポイント・実行結果は各ツールの正本に保存。機能ID／ルールID／検証ケースID、Git SHA、run ID、証跡参照、未検証状態を引き渡す。
- **FMWへの反映:** 確認できた業務知識の差分のみ、既存IDを維持して更新する。AIの提案やテストPASSを業務承認へ昇格させない。
- **互換性:** Coreは単体で動作し続ける。既存の `1.1`/`1.2`/`1.3` XSD互換、`catchup`/`change`、HTML・索引・参照を維持。
- **切替の条件:** 外部実装の利用価値と受入条件、入出力の整合性、失敗・復旧、既存経路の回帰検証、移行手順が確認できてから別PRで変更する。必要なら当面は互換アダプターを残す。
- **権限:** 調査や提案は削除・移行・本番操作・マージを許可しない。必要な影響範囲と操作は別途合意する。

この定義は新たな必須フレームワークや工程を課すものではない。変更の入口は従来どおり機能単位とし、FMWに知識の差分がなければ **NO FEATURE MAP CHANGE** とする。
