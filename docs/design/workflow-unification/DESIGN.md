# 設計書：開発ワークフローの統合

## 目的と対象

Feature Map Workflow（FMW）をソフトウェア開発の共通入口とし、既存の共通工程をFMWの工程に接続する。案件固有のゲート、管理先、接続・文字コード・提出規則は、その案件のプロファイルと専用手順で解決する。機能知識と工程案内を統合し、案件状態・実行・承認の正本を新設しない。

対象は共通Skillの入口と参照、工程とレビューの運用、既存プロファイルの受渡し、利用先の切替と旧ワークフローの保全である。顧客製品の動作変更、実DB更新、外部送信、既存案件の承認条件の変更は含まない。

## 意図と受入条件

- **BEH-001 入口**：FMWを開発プロジェクトの共通入口とする。旧開発ワークフローを呼び出す必要がなく、プロファイルがFMWへ再帰しない。
- **BEH-002 正本**：要求・受入は既存仕様や指定の設計書、実装と結果はソース・試験と原証跡、承認・進捗は指定された管理先を正本とする。Feature Mapは知識と版付き参照を持つ。
- **BEH-003 Feature Map**：各開発プロジェクトに少なくとも1つのMapを維持し、独立した機能は必要に応じて分ける。既存Mapの影響する確認済み部分を更新し、読取専用依頼では新規作成しない。
- **BEH-004 工程・ゲート**：FMWの既存工程を軸に、プロファイルのゲートと証拠を対応付ける。工程の通過だけでゲート合格や人の承認を推定せず、既存案件の条件を維持する。
- **BEH-005 検証とレビュー**：試験は変更範囲とリスクから必要十分に選び、前提状態と干渉を確認して必要な場合だけ調整する。独立レビューは重大なリスク、プロファイル、契約またはリポジトリの条件に従う。
- **BEH-006 切替と保全**：旧入口に依存する利用先を切り替え、検証済み統合版と復元可能な旧資材の所在・版・ハッシュを確認した後に、対象となる旧フォルダーを取り除く。他案件の参照を未確認のまま破壊しない。

## 検証方針

既存のFMW形式検証、Core・試験手順の回帰テスト、Skill形式、共通・案件別の参照解決を確認する。プロファイルの適用範囲が不明な場合に誤った管理先へ書き込まないこと、既存案件の承認条件が変わらないこと、実在する利用先を旧入口から移行できることを確認する。実DB・画面・顧客受入は、このワークフロー資材の静的検証から推定しない。
